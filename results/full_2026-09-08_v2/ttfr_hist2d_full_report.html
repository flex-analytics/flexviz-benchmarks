Methodology

Claim boundary. This is an end-to-end comparison of each tool’s native workload — every engine runs the chart it provides, through its own documented path; known deviations and configuration choices are listed in Run notes below. The workloads are therefore not algorithm-equivalent (a pixel-driven M4 reduction, a fixed equal-width-bucket envelope and a full raw-line rasterization are different computations), so these numbers support no equal-work algorithm-speed claims: they say what each tool does when asked for its own chart of this data, and nothing more.

Timing. Clocked entirely in the browser, from the request that triggers a tool’s pipeline to a double-rAF post-render barrier (a frame barrier after the render commit — not a claim that compositor presentation is proven; the barrier is inside the reported time). Components: server_ms = request → first byte, or a Server-Timing duration where that covers the whole server pipeline; transfer_ms = body receive; client_ms = last byte → barrier. A component a pipeline cannot separate is null and renders as “not separable” — never as zero, never back-derived from the total. Axis-extent discovery runs inside the timed window, on the tool’s own engine.

Disk policy. Disk-source repeats, when present, re-scan the file into a cold engine. The harness does not drop the OS page cache, and the cold memory trial plus warmup precede recorded repeats, so those repeats normally see a warm OS page cache. No engine result cache is shared across trials. These are engine-and-decompression timings, not controlled cold-storage I/O benchmarks.

Memory. One cold, process-isolated trial per cell, never the warm timing repeats (a reused process’s allocator collapses peak-minus-baseline deltas to noise). Backend peaks come from the kernel’s VmHWM high-water mark; in-browser store footprints from PSS (summing RSS over a Chromium tree double-counts shared pages). Raw deltas are stored in the JSON and clamped at 0 for display.

Browser. Chromium is launched with --use-angle=vulkan --enable-features=Vulkan for every contender: headless Chromium otherwise binds SwiftShader, a CPU rasterizer that cost a GPU-rendered chart 33× at 1M rows. That is a uniform, non-default browser flag — the renderer it actually bound is recorded in the provenance table below.

Run notes

  • perspective-server is excluded from the hist2d chart (unsupported): perspective has no continuous 2-D binning: viewer-charts 5.2's "Heatmap" is a categorical pivot grid over group_by/split_by and its "Density" is a radial-splat KDE with no bin count (docs/superpowers/specs/2026-08-22-perspective5-gate.md), so the grid would have to be binned outside the tool.
  • perspective-wasm is excluded from the hist2d chart (unsupported): perspective has no continuous 2-D binning: viewer-charts 5.2's "Heatmap" is a categorical pivot grid over group_by/split_by and its "Density" is a radial-splat KDE with no bin count (docs/superpowers/specs/2026-08-22-perspective5-gate.md), so the grid would have to be binned outside the tool.
  • flexviz: the timed window starts at the single POST /dashboard/update and ends at the post-render barrier. The page requests its data first and draws each figure once, with Plotly.react on the response, so there is no draw before the request to leave outside the clock: the Plotly bootstrap mosaic (t0 before vg.plot) and perspective (t0 before viewer.load) carry inside their windows is inside flexviz's too. server_ms/transfer_ms/client_ms come from that same request entry, so the three sum to total_ms up to the sub-millisecond slack between the fetch call and requestStart.
  • flexviz's timing pass runs against ONE in-driver server started once per matrix, while mosaic-server is spawned fresh per trial. Process spawn and engine import are outside every window either way, but allocator and thread-pool warmth are not the same across the two.
  • hist2d runs at n_traces=1 only: overlaid heatmaps occlude one another, and vaex-viz draws a pair of them as SUBPLOTS — a different picture, not a denser one.
  • flexviz draws the grid with Figure.add_histogram2d(x_bins=bins, y_bins=bins): the fixed_hist2d Rust kernel on a resident frame, and on a disk source a streaming group-by over a combined (xbin, ybin) key that resolves the two axes' extents in a separate collect first — both passes inside the timed window.
  • mosaic renders vg.raster with width/height pinned to the bin count, forcing a bins x bins grid instead of vgplot's pixel-driven default; fill:'density' is vgplot's own count-per-cell channel and bandwidth stays at its 0 default, so the image is the unsmoothed counts. vgplot pads its raster bins (the grid spans bins-1 intervals plus an edge), so mosaic's cell edges are not the flush numpy bins.
  • vaex draws df.viz.heatmap(x, y, shape=(bins, bins), limits='minmax') onto one matplotlib Agg figure — its own count(binby=[x, y]) kernel bins, half-open on both axes, so rows sitting exactly on either maximum fall outside the grid. vaex-viz 0.6 calls a matplotlib colormap entry point removed in matplotlib 3.9; the harness re-aliases it before the memory baseline and outside every timed window, and nothing in the binning or drawing path is changed.
  • datashader bins with Canvas(plot_width=bins, plot_height=bins).points(x, y, agg=count()) and shades the grid to a PNG; the axis extents come from the same fused dask min/max pass the line workload uses, inside the timed window.
  • altair-vegafusion bins with alt.Bin(maxbins=bins): Vega's bin picks a nice step ({1,2,5}x10^n) over the engine-computed extent, so the realised bin count moves with the data range — ~84 bins at 1M rows and ~52 at 10M on this data, where the other tools draw exactly `bins`. Exact bins would need the extent computed outside the engine, so the nicing is kept and disclosed; the gate checks counts on the engine's own edges.
  • altair-vegafusion's window is a GET /spec.json that runs VegaFusion's pre_transform_spec (DataFusion: extent, bin, aggregate) inside the request and returns the Vega spec with the binned rows inlined; the browser parses it with vega and awaits View.runAsync(). server_ms is the Server-Timing of that whole server pipeline, JSON serialisation included. The VegaFusion task-graph cache is cleared before every request, since otherwise every repeat after the first is a cache read.
  • altair-vegafusion's store: in-memory the polars frame is handed to VegaFusion over the Arrow C stream without a copy; on a disk source the file path is the chart's data url and DataFusion scans the Parquet inside the request.
  • VegaFusion runs a single engine: the DuckDB SQL connection was removed in VegaFusion 2.0 (2024-11-13); a duckdb relation is still accepted as an inline dataset but is converted to Arrow and DataFusion evaluates the plan, so a duckdb-backed entry would be the same measurement under a different name.
  • mosaic-server on a disk source is loaded as a VIEW over the file, so the scan stays inside the timed window. This is a disclosed deviation from Mosaic's loadParquet default, which materializes a table before any query runs; the in-memory cells do use that materializing default.
  • mosaic-wasm compute in the browser and are benchmarked in-memory ONLY: the disk cells are out of scope by benchmark design, not because the engines lack a file path. Those cells are recorded as source_out_of_scope, never as failures.
  • mosaic-wasm lets DuckDB-WASM pick its own build: selectBundle() feature detection over the vendored `mvp` and `eh` candidates — the documented default path, single-threaded. The experimental COI/pthreads build is not vendored (it needs cross-origin isolation, which changes the page's capabilities). The selected bundle is recorded per run.
  • altair-vegafusion's store: in-memory the polars frame is handed to VegaFusion over the Arrow C stream without a copy.
  • altair-vegafusion's store: on a disk source the file path is the chart's data url and DataFusion scans the Parquet inside the request.
